Executive Summary

This document is a guide for repository builders who want to add profile-guided deposition to a research data repository. Profile-guided deposition helps depositors supply the files their community expects and record what each file means. The guide builds on the concept and demonstration presented in M5.1.2, “Profile-guided deposition: concept and demonstration”.

The guide first explains how to define shared semantic types and deposition profiles, using the interview example from M5.1.2. It then describes the components a repository needs: community configuration, deposition controls, a profile checker, search filters, a record page view, and the repository’s own file, metadata and lifecycle services. A step-by-step walkthrough shows how to install the oarepo-pgd plugin in a CESNET Invenio repository, add the interview configuration, connect the deposit form, and follow a deposit from draft to publication. Labels and guidance can be written in several languages, and the plugin’s own texts come in English and Czech.

Further examples show how the same profile format supports catch-all deposits, cryo-EM maps and molecular-dynamics simulations following the BioSim CZ architecture. The guide also outlines how processing services can use file annotations to select inputs, extract metadata and combine files in previews.

Profile-guided deposition contributes to FAIRness through explicit file expectations and machine-readable file meanings. A broader assessment of FAIRness also covers identifiers, access, licensing and preservation.

1 Introduction

Profile-guided deposition helps depositors supply the expected files and describe what they mean. Semantic types identify what individual files represent, independently of their format. A deposition profile uses these shared meanings to define file requirements and guidance for a kind of dataset. Several profiles can reuse the same semantic types.

M5.1.2, “Profile-guided deposition: concept and demonstration”, introduces the approach and its terminology and illustrates its use from the depositor’s viewpoint with an interview example: a depositor shares an interview recording, its transcript and an interview guide, and switches between profiles for recorded and transcribed interviews. This guide continues that example and extends the approach to two further kinds of data with their own profiles: cryo-EM maps and molecular-dynamics simulations. It explains how to incorporate the approach into a repository, covering the general design and its implementation in CESNET Invenio, the Invenio-based repository platform used within NRP, distributed as the OARepo software packages.

The guide uses the three roles from M5.1.2. The repository builder turns community requirements into semantic types, profiles and guidance. The depositor uploads files and reviews their annotations. Consumers are people or software that use the files and their annotations to understand or process the dataset.

The NRP analysis of procedures for implementing the FAIR principles recommends that repositories support the data standards of each research field and offer tools in the user interface for checking whether uploaded data comply. The analysis describes a repository’s rules through its metadata profile and data policy. A deposition profile adds file requirements to these rules.

The repository already uploads files, saves metadata, controls access and manages publication. Profile support adds configuration, file annotations, deposition controls and a publication check to these existing services. Within NRP, the repository’s metadata profile describes the dataset as a whole and maps it to the common Czech Core Metadata Model (CCMM) record for discovery in the National Metadata Directory. The basic extension adds two fields for file information and leaves the existing dataset description and its mappings unchanged. It stores file annotations in the repository record. Adding them to metadata exports, such as DataCite, and to the CCMM record for the National Metadata Directory is a later step.

2 Define Semantic Types and Profiles

The repository builder turns community requirements into semantic types and deposition profiles. Communities choose requirements from their standards and practices. A FAIR Implementation Profile, where available, can inform these choices. Keeping terms, constraints and guidance separate follows established application-profile practice.

Each semantic type has a stable identifier, a display label and a definition. Profiles refer to these identifiers, and file annotations record them. The repository requires an annotation for every file, and a file can carry only the types its profile permits. A builder who wants a profile to accept miscellaneous files, such as a README or a list of checksums, defines a shared type other and lists it in that profile. The depositor selects it and adds a description saying what the file is. A profile without other accepts only files that its own types describe.

Each deposition profile has an identifier, a revision, a display name, the semantic types a depositor may assign, and a list of file requirements. Each requirement has a label, a level, count limits, the semantic types that match it and guidance text for the depositor. The level sets how the repository checks the requirement:

  • Required: a count below the minimum blocks publication.
  • Recommended: a count below the minimum is shown to the depositor as a notice, and publication stays open.
  • Optional: matching files are counted and shown to the depositor.

A maximum, where set, blocks publication when exceeded at any level. The configuration must be consistent: an optional requirement has a minimum of 0, a recommended requirement has a minimum of at least 1, and a maximum is at least the minimum. Requirements that list the same semantic types count the same files, so a required minimum above another such requirement’s maximum would block every deposit; the repository refuses such a profile.

Each permitted type can also carry filename suggestions and a list of accepted formats. Filename suggestions help the form propose a type, and they belong to the profile because naming conventions differ between communities and tools. Accepted formats let the repository check that a file uses a representation the community accepts for that meaning, for example WAV or FLAC for interview recordings. The meaning itself stays independent of format: every permitted type remains selectable for any file, and the checks report a format the profile does not accept.

Requirement matches are derived from the assigned semantic types and the repository’s current file inventory. A filename suggestion becomes an assignment as soon as the file is uploaded, and the depositor can inspect and correct it. A file matches a requirement when any of its types appears in that requirement’s list. Each distinct file counts once per matching requirement. Changing the selected profile preserves file annotations and applies the new requirements to them.

The examples in this guide start from the interview example introduced in M5.1.2, “Profile-guided deposition: concept and demonstration”. In that example, a depositor shares an interview recording, its transcript and an interview guide. The example uses three shared semantic types and two deposition profiles. The semantic types are defined as follows:

- id: interview-recording
  label: Interview recording
  definition: A recording of an interview session.
- id: interview-transcript
  label: Interview transcript
  definition: A written transcription of an interview session.
- id: interview-guide
  label: Interview guide
  definition: The questions or prompts used by the interviewer.

These local identifiers work within one repository. When annotations are exported or shared, consumers need the published definitions or the persistent URI of an equivalent community term.

The two profiles share these definitions and specify the file requirements in Table 1.

Table 1. File requirements for the two illustrative interview profiles.
Profile Required file Optional supporting files
Recorded interview At least one interview recording. Interview transcript and interview guide.
Transcribed interview At least one interview transcript. Interview guide.

The Transcribed interview profile is shown below in the configuration format used by the implementation walkthrough, with shortened guidance and fewer filename patterns:

id: transcribed-interview
revision: "1.0"
dataset_category: Transcribed interview
semantic_types:
  - id: interview-transcript
    filename_patterns: ["interview.txt", "*transcript*.pdf"]
    formats: [txt, pdf, docx]
  - id: interview-guide
    filename_patterns: ["*guide*.pdf"]
requirements:
  - id: transcripts
    label: Transcripts
    level: required
    min_files: 1
    semantic_types: [interview-transcript]
    help: Provide a written transcription of the interview.
  - id: guides
    label: Interview guides
    level: optional
    min_files: 0
    semantic_types: [interview-guide]
    help: Add the questions or prompts used by the interviewer.

The profile’s id and revision identify the configuration applied to a deposit, and dataset_category supplies its display name. The profile’s semantic_types list names the permitted types; a file can carry only these types. Their filename_patterns pre-select a type for matching uploads, which the depositor can change. When several patterns match, the most specific one decides; if equally specific patterns belong to different types, no type is pre-selected. The optional formats list names the accepted formats, identified here by file suffix; the guide type omits it and accepts any format. A repository can also identify formats from file content. Each entry in requirements sets its level, a min_files count and an optional max_files count; omitting max_files leaves the upper count unrestricted. The help text explains what to provide. The exact pattern interview.txt matches the transcript filename used in the M5.1.2 example.

3 Implementation Walkthrough: CESNET Invenio

A CESNET Invenio repository already uploads files, saves metadata, controls access and manages publication. The oarepo-pgd plugin, version 0.4.1, adds profile-guided deposition to these services. To use it, the repository builder first installs the plugin, enables it on the dataset model and connects the deposit form. These are manual steps, done once. The builder then describes the community’s files as semantic types and deposition profiles in YAML files next to the model. The plugin supplies the deposition controls, the profile checker, the search filters and the record page view. Figure 1 shows these parts and who supplies them.

The green rectangle is configuration; yellow rounded boxes are activities. Unfilled dashed boundaries show who supplies each part. Table 2 explains what each part does.

Table 2. Parts of the implementation and their responsibilities.
Part Supplied by What it does
Semantic types and deposition profiles Repository builder YAML files define file meanings, requirements and guidance. The builder writes them with domain scientists.
Deposition controls Plugin In the deposit form, the depositor selects a profile, reviews the suggested type of each file and sees the requirement counts.
Profile checker Plugin On the server, it checks the annotations and requirements against the draft’s current files on every save and before publication.
Search filters Plugin On the search page and in the search API, readers filter published datasets by dataset category and by file type, with labels in their language.
Record page view Plugin On a record’s page, it lists each file with its semantic types and description, for readers who may read the files.
File, metadata and lifecycle services CESNET Invenio They save the deposit with its annotations, supply the authoritative file list and apply the publication check for all clients.
Consumers People and software They interpret or process the published files using the annotations.

The following steps are for a repository generated from the standard CESNET Invenio templates on oarepo-app 8 (OARepo 14.2, InvenioRDM 14), and they describe version 0.4.1 of the plugin. They say what the repository builder does and why. The plugin’s README for that version gives the exact commands and code, and the README of a later version describes that version’s steps. The demonstrator repository records the result of these steps as tags:

  • d5.1.3-baseline is the generated repository with a dataset model, offering English and Czech.
  • d5.1.3-plugin adds the installed and connected plugin with the interview configuration. 3.1 Install the Plugin and Enable It on the Model

The builder adds the plugin’s tagged release to the repository’s dependencies and enables the plugin on the dataset model. Enabling it adds two metadata fields to the model, one for the selected profile and one for the file annotations, so the model’s own metadata description stays unchanged. The plugin reads its configuration from a directory next to the model and finds the model’s deposit form through the model’s user interface configuration. A repository generated from the standard templates already follows these conventions.

3.2 Add the Interview Configuration

The configuration lives in two directories next to the model:

  • models/datasets/config/semantic-types/ holds the semantic types. Place the three interview types shown above in interviews.yaml.
  • models/datasets/config/profiles/ holds one file per profile. Place the Transcribed interview profile in transcribed-interview.yaml. Add recorded-interview.yaml with the same structure, a required recording, an optional transcript and an optional guide.

The plugin reads every YAML file (.yaml or .yml) in both directories at startup. Each label, definition, profile name and help text is either one text or a mapping of language codes to texts, such as {en: Interview transcript, cs: Přepis rozhovoru}. The repository shows each reader the text in their language, with English as the fallback; the plugin’s own texts come in English and Czech. A mistake in a file, such as a repeated key, stops startup with a message naming the file and line. An enabled model needs at least one profile.

3.3 Connect the Deposit Form

The builder adds the plugin’s component to the model’s user interface configuration and includes the plugin’s template in the model’s record page. The component passes the configuration to the deposit form and the file meanings to the record page. After the repository is installed again, the standard tabbed form renames its files tab to Files and meanings and shows the profile controls there. When a model has only one profile, the form selects it for a draft that has none. The controls use the repository’s theme, so the plugin brings no stylesheet and needs no change to the repository’s JavaScript.

A repository whose search index was created before the plugin was installed also rebuilds that index, because the two metadata fields are new to it, and drafts with a profile cannot be saved until the index has them. Search results are incomplete until the records are indexed again, so the builder plans the rebuild like other maintenance. The plugin’s README gives the procedure.

A repository can change how the controls look while the plugin keeps the checks: the profile selector, the requirement cards, the file assignments table and the semantic definitions can each be replaced by the repository’s own component, and the record page table by the repository’s own template. A repository with its own deposit form places the controls itself. The plugin’s deposit form documentation describes both. An independent frontend or other software uses two endpoints of the plugin: one serves the configuration, and one checks a saved draft and returns each problem with a code, together with the file count and state of each requirement. The plugin’s API documentation describes both endpoints, the two fields and what saving and publication report.

3.4 Follow a Deposit from Draft to Publication

In Files and meanings, the depositor selects Transcribed interview. With no files, the transcript requirement counts 0 of at least 1 file. After the upload of interview.txt, the filename pattern suggests Interview transcript, and the depositor can change the assignment. With that meaning assigned, the file satisfies the transcript requirement; an interview guide remains optional. The form shows the counts and marks each rule that still fails.

The saved draft stores the selected profile and one annotation for each file in its metadata:

{
  "pgd_deposition_profile": {"id": "transcribed-interview", "revision": "1.0"},
  "pgd_file_annotations": [
    {
      "file_key": "interview.txt",
      "semantic_types": ["interview-transcript"],
      "description": "Transcript of the interview"
    }
  ]
}

Here file_key is the name under which the repository stores the file in the record, exactly as the depositor’s computer supplied it. The depositor selects the profile by name, and the plugin records its revision.

The profile checker runs on the server for every draft that has files enabled, including a draft with no uploads yet. It checks the selected profile and revision, the file annotations and the configured counts against the draft’s current files, and checks accepted formats by filename suffix. Only completed uploads count, so a publish request cannot rely on a file that is still uploading. A draft save reports the errors and keeps the draft. The same errors block publication through the form, a publish request or the API. A recommended requirement below its minimum is marked in yellow in the form and leaves publication open. A record with files disabled has no files to describe, so the form and the server apply no profile to it.

After publication, the record’s page shows a File meanings table with the selected profile and each file’s semantic types and description. The search page offers two filters, Dataset category and File types, labelled from the configuration.

File annotations name and describe the files, so they follow the record’s file access. A reader who may not access a record’s files sees no annotations on its page or through the record API. The search index holds the annotations only of records whose files anyone may read, so a search or the File types filter cannot reveal restricted files; a record with restricted files is still found by its dataset category.

4 Configure Other Datasets

To support another domain, add its meanings, requirements and filename hints to the model’s configuration directories. The plugin uses the same metadata fields, endpoint, deposition controls and schema check for the new profiles. The examples below show configuration choices and identify where additional support is needed. The demonstrator repository adds each example as a further tag, and the difference from the preceding tag contains only YAML files.

Before a profile goes into use, domain scientists review it against representative deposits and counterexamples. The plugin’s tests show that the configured rules are applied correctly; this review shows that they are the right rules for the community.

4.1 Catch-All Deposits

A repository accepting diverse material can use a profile without requirements that permits the shared other type, together with any specific types it wants to offer:

id: general-dataset
revision: "1.0"
dataset_category: General dataset
semantic_types:
  - id: other
    filename_patterns: ["*"]
requirements: []

The pattern "*" is the least specific pattern, so it pre-selects other for every file that no more specific pattern matches. Set requires_description: true in the shared semantic-type definition for other to require a description whenever it is assigned, and search_filter: false to keep it out of the File types search filter, where it would match almost every general deposit. The depositor changes the files that deserve a specific meaning and describes the rest. The same rule applies as in the interview profiles: every file carries an annotation.

The demonstrator adds this profile in the tag d5.1.3-catch-all (difference from the plugin tag).

4.2 Cryo-EM Maps

Cryo-electron microscopy (cryo-EM) reconstructs the three-dimensional shape of a molecule as a density map, a volume of values on a regular grid. The Electron Microscopy Data Bank (EMDB) archives such maps under published rules. Every entry has one primary map. Since 2022, entries from single-particle analysis and subtomogram averaging also need two half maps, each reconstructed from one half of the data. Masks and other additional maps are optional. Table 3 shows a profile modelled on these rules.

Table 3. Illustrative file requirements for a cryo-EM map deposit.
Requirement Level / count Semantic type
Primary map Required / exactly 1 primary_map
Half maps Required / exactly 2 half_map
Masks Recommended / at least 1 mask
Segmentations Optional segmentation

The maps and masks usually share one format, such as MRC, so the format cannot tell a primary map from a half map or a mask. The meaning comes from the depositor: filename patterns such as *half*.mrc suggest a type, and the depositor confirms or corrects it. The counts express pairing without links between files. With exactly two half maps in the deposit, a validation service finds both by their type and computes the resolution estimate from them. The profile recommends masks, although EMDB treats them as optional, because the mask applied during processing is needed to reproduce that estimate.

Some relationships need more than file counts. A segmentation refers to the map it was drawn on, which a profile cannot state when a deposit holds several maps. Multipart images and OME-Zarr stores, where one logical image spans many files, need a packaging convention before their files can be counted.

The demonstrator adds the four types and the profile in the tag d5.1.3-cryo-em (difference from the catch-all tag).

4.3 Molecular Dynamics

Molecular dynamics simulates the motion of atoms in a molecular system. A deposit typically holds prepared simulation inputs, files describing the molecular system, and the resulting trajectories. The BioSim CZ architecture describes a repository for such data, and this example follows it.

In that architecture, a study contains one or more experiments. Each experiment is one simulation setup or run with its own files, and the depositor confirms a semantic type for each file from a shared vocabulary. The vocabulary links each type to a class of the Molecular Simulation Ontology (MOLSIM), such as http://purl.obolibrary.org/obo/MOLSIM_001091 for topologies; in the configuration, this link becomes the type’s uri. The architecture lists the files of a GROMACS experiment with their requirement levels, and these translate directly into a deposition profile, as Table 4 shows.

Table 4. Illustrative GROMACS file requirements for one experiment.
Requirement Level / count Semantic type Typical files
Run input Required / exactly 1 run_input TPR
Topology Recommended / at least 1 topology TOP, ITP
Structure Recommended / at least 1 structure GRO
Run parameters Optional parameter_file MDP
Trajectories Optional trajectory XTC, TRR

Filename patterns such as *.tpr pre-select a type, and the depositor confirms or corrects it. The limit of exactly one run input reflects how the files are used later: a processing service reads one run input per simulation, and the limit lets it find that file from its type alone. The profile needs community review before adoption as a deposition standard.

The files of one experiment belong together, because they describe the same simulation. Grouping files into experiments and checking every experiment before the study is published are the repository’s responsibilities. The profile format stays the same.

The demonstrator adds the GROMACS profile and its types in the tag d5.1.3-molecular-dynamics (difference from the cryo-EM tag). There the profile applies to a whole deposit, which stands for one experiment.

5 Use Annotations in Processing

A repository often processes the files it holds: it reads metadata from them, prepares previews or checks their content. Every such processing service first has to find out which tool applies to a deposit, which file plays which part, and whether its inputs are complete. File names give an unreliable answer. Many tools leave naming to the user, and one extension can stand for several kinds of file. A service that works from names carries its own naming rules for every tool and guesses when they fail.

A deposit made under a profile already holds these answers, as Table 5 shows.

Table 5. What a processing service needs to know and where a deposit provides it.
The service needs to know The deposit provides
Which tool applies The selected profile, for example GROMACS.
Which file plays which part The semantic types, suggested by the form and confirmed by the depositor.
Whether the inputs are complete The required files, checked before publication.
Which rules applied The profile revision stored with the deposit.

A service might need several files of a deposit, each for a different purpose. It finds them through the annotations. The type says what a file is. A count limit makes a file unique: a GROMACS deposit has exactly one run input, so the service needs no further choice. Where several files share a type, the format tells them apart: a GROMACS topology in TOP format is the main topology, and ITP files of the same type hold parts that it includes.

Repository builders can plan for this when they write a profile. They ask what the services that later read the deposit need, make those files required, and limit a type to one file where a service reads exactly one.

Two kinds of service show how this works:

  • Metadata extraction. The BioSim CZ architecture describes it for molecular dynamics. The profile identifies the simulation software and with it the extractor to use. The extractor reads the run input as its main source, and the topology and the structure for values the run input lacks, such as the force field or the box geometry. It finds each of these files by its type. An adaptor then maps the values to the repository’s metadata fields and vocabularies, converting units where needed, and the depositor reviews the proposed values.
  • File previews. A previewer usually shows one file at a time and chooses how to show it from the file’s format. Some files need a partner. A trajectory holds only atom positions, so a viewer can draw it only together with a structure, and a cryo-EM map is easier to judge with its mask. A previewer that asks the repository which files belong to the previewed one can load them together: the trajectory plays on the structure of the same deposit, and the primary map appears with its mask. Files without a specific type are previewed one at a time, and a trajectory among them has no preview.

In both cases the depositor gains from the types they assigned: the repository proposes metadata read from the files and shows the dataset as a whole. An annotation records what the depositor confirmed. A service still checks that a file’s content fits its type, for example that a trajectory and its structure have the same number of atoms, and reports a mismatch separately from the profile check.

The plugin stores the profile and the annotations. Extraction and previews are separate components and require their own implementation. Other consumers can use annotations for semantic grouping or further discovery filters, with their own display components or indexing.

6 Contribution to FAIRness

Profile-guided deposition contributes to the FAIR principles in specific ways. Some contributions come with the plugin, and others need further work by the repository builder.

With the plugin installed, the repository:

  • states the expected files for each kind of dataset and checks them before publication, which helps deposits arrive complete;
  • saves each file’s semantic types and description in the record, where people and software that may access the files read them through the record API and on the record page;
  • records which profile and revision each deposit was checked against;
  • offers two search filters, Dataset category for the selected profile and File types for the semantic types of the files, so that people find datasets with the files they need, for example every dataset that contains an interview transcript under either interview profile.

Two further steps by the builder extend these contributions:

  • Community terms: link each semantic type to an established community vocabulary term through the optional uri field of its definition, so that other repositories and tools interpret the annotations in the same way.
  • Metadata exports: map the annotations into DataCite and into the CCMM record for the National Metadata Directory, so that the file meanings reach services outside the repository. The CESNET Invenio documentation describes how to customise and add export formats.

Report profile conformance and content checks as separate results. Profile conformance says which files are present and how they are described; a content check says whether a file’s content is valid for its type. An overall FAIR assessment also covers identifiers, access, licensing and preservation, and needs a broader method such as the RDA FAIR Data Maturity Model.

7 Conclusion

This guide described how to add profile-guided deposition to a repository. The repository builder works with domain scientists to define shared semantic types and deposition profiles. Deposition controls help depositors assign file meanings and show which requirements their files meet. A profile checker applies the same rules on the server: depositors can save incomplete drafts, and publication is blocked until the required files are present and correctly annotated. The repository keeps its existing services for files, metadata, access and publication.

In CESNET Invenio, the oarepo-pgd plugin provides these components. A repository installs the plugin, enables it on the dataset model, adds its configuration files and connects the deposit form. Other domains can be supported by adding configuration, as long as their requirements can be expressed as file counts. Relationships between files, grouping files into experiments and metadata extraction need further implementation, as the cryo-EM and molecular-dynamics examples show.

Before adoption, domain scientists should review the profiles against representative deposits. A repository with its own deposit form or publication workflow should also make one test deposit through the form and one through the API. Shared definitions based on established community vocabulary terms make the annotations useful beyond a single repository.
